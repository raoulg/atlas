One rule, the same in Python, TypeScript and Rust: a name a function binds is the value it bound, with the type that
value was given, and never the module's function of that name. It closes two issues.

- **A local named like a function of its module is the local** (#375). In TypeScript, `const size = addressed.length;
  pile.counts.push(size)` drew a step `size`, as if the module's function `size` were handed on, and `const tidy = (s:
  string) => s.trim().toLowerCase(); tidy(l.to)` drew a call of the module's `tidy`. Now both are the body's own values,
  as Python and Rust already read them. Where no local takes the name, the function is still the module's:
  `piles.map(size)` runs `size` on each pile.
- **A value a change gives anew keeps its type** (#394). After `rows[0]!.push(second)`, TypeScript handed `show` the
  rows with no type, and after `both.push(second)` the change itself gave `both` with none; Rust did the same where the
  list starts at a module's value (`vec![&QUIET]`). Now the step after the change is handed what the change gave,
  `Level · rows`, as Python reads it.

```text
example: engine/tests/pairs/shadows/typescript/shortcut, route inbox.sort
  before   sort runs inbox.tidy, inbox.size
  after    sort runs none of the program's functions, as its clean side and Python and Rust do
example: engine/tests/pairs/lookups/typescript/clean, route signal.grown
  before   Level · rows → push → Level · rows → show handed · rows
  after    Level · rows → push → Level · rows → show handed Level · rows
```
