One rule, the same in Python, TypeScript and Rust: a name a function binds is the value it bound, with the type that
value was given, and never the module's function of that name. It closes two issues.

- **A local named like a function of its module is the local** (#375). In TypeScript, `const size = addressed.length;
  pile.counts.push(size)` drew a step `size`, as if the module's function `size` were handed on, and `const tidy = (s:
  string) => s.trim().toLowerCase(); tidy(l.to)` drew a call of the module's `tidy`. Now both are the body's own values,
  as Python and Rust already read them. Where no local takes the name, the function is still the module's:
  `piles.map(size)` runs `size` on each pile.
- **A value a change gives anew keeps its type** (#394). After `rows[0]!.push(second)`, TypeScript handed `show` the
  rows with no type, and after `both.push(second)` the change itself gave `both` with none; Rust did the same where the
  list starts at a module's value (`vec![&QUIET]`). Now the step after the change is handed what the change gave,
  `Level · rows`, as Python reads it.

```text
example: engine/tests/pairs/shadows/typescript/shortcut, route inbox.sort
  before   sort runs inbox.tidy, inbox.size
  after    sort runs none of the program's functions, as its clean side and Python and Rust do
example: engine/tests/pairs/lookups/typescript/clean, route signal.grown
  before   Level · rows → push → Level · rows → show handed · rows
  after    Level · rows → push → Level · rows → show handed Level · rows
```

**The rule, and where it lives.** A name has two faces: whether the body binds it where it stands (then it is never
the module's), and what type it holds there. The second is shared and belongs in `engine/src/body.rs`; the first is
each language's scope and stays with the reader.

1. *One table of kept values, with their types* (`body.rs`). `Steps::kept` (`body.rs:365`) is a `HashSet<String>` and
   `Steps::keep` (`body.rs:1465`) throws the type of each `Held` away. Replace the set by a type `Kept` in `body.rs`: of
   each name the steps so far gave, the values the latest step that gave it gave under that name, with their types.
   It answers `contains(name)` as the set did, and one lookup, `Kept::value_of(name: &str, bound: bool) ->
   Option<Vec<Held>>`: where a step gave the name, those values (`Held::new(ty, name)`, typed where the step typed
   them); else where `bound` (the reader says the body binds it here), one value of no type; else `None`, and only
   then is the name the module's, for the reader's resolver. The readers pass `&steps.kept` where they now pass the
   set (`kept: &HashSet<String>`: 8 signatures in `typescript/body.rs`, 6 in `rust/body.rs`, `made` in
   `python/body.rs`, which clones it at `python/body.rs:1335`). TypeScript's cache of `held` keys on `kept.len()`
   (`typescript/body.rs:1349`, "kept only grows"); a table whose types change for a name it holds must key on
   something that changes with every `keep` (a count of what it was given), or the cache hands a stale type.
2. *The readers ask it before their module resolver.*
   - TypeScript `handed_on`, `typescript/body.rs:1719`: l.1726 resolves the identifier in the module
     (`self.resolve(&[text(c, ..)])`) without asking whether the body binds it. Ask
     `steps.kept.value_of(name, self.locals.bound(c, src))` first and hand nothing on when it is `Some`.
   - TypeScript `callee`, `typescript/body.rs:1774`: l.1790 `self.resolve(&parts)` resolves a call by a local's name in
     the module. Where `f` is one identifier the body binds (`self.locals.bound(f, src)`, `typescript/body.rs:323`) the
     call reaches no function of the module, as `type_of` already decides for a value (`typescript/body.rs:645`). A
     kept name is always a binding, so `bound` alone answers here, where no `Steps` is at hand. `rendered`
     (`typescript/body.rs:1711`, `<Row/>` of a local `const Row = ..`) is the same form; give it the same question.
   - TypeScript `held_anew`, `typescript/body.rs:1410`: `kept.contains(name)` returns `Held::new("", name)`. Push
     `kept.value_of(name, false)` instead.
   - TypeScript `changes`, `typescript/body.rs:1994`: l.2017 gives the changed value with `self.type_of(owner)`, which
     knows only class bindings, so `both.push(second)` gives `· both` although the same step is handed `Level · both`.
     Give the owner the values `held` finds for it (as the `part` branch above it does, l.2008), so the table in (1)
     keeps the type the change was handed. Without this, (1) does not reach `pushed`.
   - Rust `held_by`, `rust/body.rs:2015`: l.2029 `None if kept.contains(&name)` gives `Held::at(String::new(), ..)`.
     Take the type from `kept.value_of(&name, false)`.
   - Rust `handed_on`, `rust/body.rs:2258`, already holds the first face: `resolve_value` (`rust/body.rs:1004`) asks
     `module::shadowed` (`rust/module.rs:630`, the names `bound_at` finds) before the module. Leave it, or let it ask
     `value_of` with `shadowed(..)` as `bound`; it must stay green.
   - Python `held`, `python/body.rs:909`: l.966 gives a name ty does not type `String::new()` where `made` (the kept
     table) holds it. Take the type from `made.value_of(name, false)`. Green today only because ty types `rows` and
     `both`; this keeps the one form where it does not.
   - Python `handed_function`, `python/body.rs:796`, is scope-aware through ty (a local's definition is no function
     node); its fallback `self.bound(a)` (l.809, `python/body.rs:1084`) asks the module only when ty reached nothing.
     Leave it.
3. *What each reader keeps*: its module resolver (`resolve` in each `body.rs`), its scope (`Locals` on `body::Bindings`
   in TypeScript, `module::bound_at`/`shadowed` in Rust, ty's definitions in Python) and its identifier node kinds
   (`identifier`, Rust's `scoped_identifier`, Python's `attribute` in `handed_on`). `body.rs` knows no scope and should
   not learn one here: it owns the kept table and the order of asking.
