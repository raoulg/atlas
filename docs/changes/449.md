A door that reads or writes the file its caller hands it is drawn as that hole, named by its parameter:
`Disk(load.path)` for `pd.read_csv(path)` as `Disk(download.to)` for `to.write_bytes(..)`. Before, a read whose
operation says a format was drawn as a pattern of that format, `File(*.csv)` beside `Disk(download.to)`: two
spellings of one construct, and a pattern the code never writes. The format is still what the code knows of a file
no term names, such as a stream handed in (`File(*.json)` of `json.load(f)`). The same holds for `Plot.save`: its
figure is `Disk(Plot.save.to)`, not `File(*.png)`.

In the sunspots pipeline the export view drew the download and the read as two places, although the command hands
both the same file. The library did not say they share it: only the command did. So the pipeline now says it: the
library keeps the raw file at `RAW` unless told, and `download` and `load` default to it (`to: Path = RAW`,
`to: string = RAW`, `Option<&Path>` unwrapped to `RAW` in Rust). Every door alone, and the view of all of them, draws
one file, `File(data/raw/sunspots.csv)`, written by `download` and read by `load`.

A Rust constant a binary imports from its library crate through a re-export (`use sunspots::RAW` where `lib.rs`
says `pub use series::RAW`) is the constant it leads to, not a value Atlas does not know.

The law `a_file_the_caller_names_is_its_term_whatever_its_format` holds the first point in every language on the
pair `formats`. Rust makes the fallback of `path.unwrap_or(..)` whole in the door itself, where Python and TypeScript
make a declared default whole by the caller or the door's users: #450.

Kind: drawn wrong, now right.
