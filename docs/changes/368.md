What ran before a step decides where it reads and writes, and Atlas now asks it of the object the step runs on, not of
its class. When a route sets up two shelves and then reads from one of them, the read counts the set-up that built that
shelf alone. In the shortcut of the `order` pair, `review` keeps its report in `out`, sets the drafts up and reads the
report from them: the read now reads `drafts/report.txt` only, and `review` no longer seems to read back the report it
kept in `out`, a file it never reads.

The same rule settles a call in a loop (#354). A name the loop rebinds after a call holds, in the next round, what the
rebinding made, so the call is handed both values: in `setup-in-a-loop`, `keep_report` takes the drafts in the first
round and the shelf `open_shelf` opened in every later one, and the picture draws the line from each.

Python, Rust and TypeScript read alike: the `order` and `setup` pairs and `setup-in-a-loop` are written in all three,
and the engine and the page give one reading of each.

```text
plans/setup-in-a-loop, the line into keep_report's write   before: Shelf·shelf@main/open_drafts
                                                           after:  Shelf·shelf@main/open_drafts, Shelf·shelf@main/open_shelf
pairs/order shortcut, what the read under Shelf.report     before: File(drafts/report.txt), File(out/report.txt)
reads                                                      after:  File(drafts/report.txt)
pairs/order shortcut, what review reads back               before: out/report.txt
                                                           after:  nothing
```

Still open:

- Where the body does not say which object a method runs on (a parameter, a field of the object a method runs on, a
  value its own code binds), any set-up of the class that ran before still counts.
- A call in a loop whose own result rebinds the name it runs on (`shelf = shelf.next()`) is not handed what it made in
  the round before.
