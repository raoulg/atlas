A method a family only declares (an `@abstractmethod`, a `Protocol`'s method, a trait's method without a default body,
a TypeScript `abstract` or `interface` method) runs no body. The overview and a focus drew its signature as if it were
code of its own: on vectormesh, `BaseAggregator` took a 3D tensor and gave a 2D one. Now such a method takes, gives and
touches nothing in every view; its class draws only what its concrete code does, and a call of it draws the members
that fill it in, each of them where the code does not say which one runs. A base method with a body of its own, a
default its members override, is still drawn as the code it is.

## For the implementer

The law is written; the code is yours. Do not change the pair or the tests to make them pass: a test that moves is a
question about the law, put to the issue.

### What holds and what is red

The pair is `engine/tests/pairs/abstract/{python,rust,typescript}/{clean,shortcut}`: two families, `Exporter.export`
(CSV and JSON members, each writing its own file) and `Store.keep` (`Shelf`, `Vault`), each called by an entry

### The rule, and its one shared place

A function with no body has an empty own arrow; its signature is the family's type, never an arrow; a call of it is the
coproduct of its members (`docs/reference/mathematics.md`, Coproducts). Every reader already says which function has no
body (`Node::declared`); nothing downstream reads it when it forms an arrow. So the rule is written once, where arrows
are formed, and no reader changes its control flow:

1. **`engine/src/flow.rs`, `arrow_of` (line 1225).** For `n.declared`, the arrow is empty: no `takes`, `gives`,
   `changes`, `builds`, `gives_back`, `returns_value`. Keep `receiver` if the route plans need it to hand the call's
   value to the member (`plan.js` lines 1138, 1182, 1586 read it); check with law (b).
2. **`engine/src/families.rs`, `families` (line 195).** `makes`/`takes` are read off the `Takes`/`Returns`/`Mutates`
   edges; skip a source that is `declared`. This is what the overview and a focus read (`TYPES.makes`/`takes` in
   `plan.js`, `typeUse` at line 497), so `typeUse` itself needs no change.
3. **`viewer/plan.js`, `usesOf` (line 499).** The diff branch (`SIDE`) reads the edges itself: skip a source whose node
   is `declared`, as `families` does. Keep your `plan.js` change to `usesOf` and `typeUse`: #431 is changing the
   overview's type lattice in the same file at the same time.
4. **`engine/tests/plans.mjs`, `arrowFaults` (line 550)** holds the law "each function's arrow in `F₀` is its
   morphism", read off `D.edges`. A declared method keeps its signature's edges, so this law would now flag it: skip
   `n.declared` there, and say so in `engine/tests/plans/README.md` (the sentence "Each function's arrow there is its
   morphism", line 26): a declared method has none.

Keep the `Takes`/`Returns` edges of a declared method. They are the signature, a fact of the graph (the map is not the
territory: a picture is made coarser by zoom and filters, never by dropping a fact), and the `overrides` principle
compares members against it (`principles.rs:805`, through `Node::params`/`returns`).

### The trap: the call's arrow is read from the declared method

Emptying `arrow_of` alone breaks law (b) in Rust: `publish/Exporter.export hands on {}, its members hand back
{"Receipt"}`. That was tried on this branch and reverted. The reason: a route's step for a call into a family is keyed
by the declared method's id, and `plan.js` reads that step's arrow with `arrowOf(stepOf(key))` (`morphism` at line
1039, `handsBack` at line 1081). Two quantities share one id: the declared method's own arrow and the arrow of a call
of it. Sentence 6 says they are never merged. Python survives because its call site already names the value it gives
(`Site::gives: [{type: Receipt}]`, from ty). The Rust site of `exporter_for(format).export(report)` has no `gives`, so
its plan falls back on the declared method's arrow. TypeScript held law (b) with the arrow wholly empty. With only
`returns_value` kept, it drew `publish/Exporter.export > publish back` in place of the Receipt it hands on, so its
plan reads the same fields too.

The fix that stays outside `plan.js`'s route code: a call of a declared method gives a value of the type its signature
declares. That is the caller's value, typed by the family's signature, and not the method's own arrow. Write it once
in `builder.rs`, where the graph is made whole (`finish`, line 360, beside `settle_fails` at line 374): for each site
whose `to` is `declared` and that names no `gives`, give it the types of the callee's `Returns` edges. No reader's
`body.rs` changes (K9 is in `body.rs`). If that does not restore law (b) in Rust and TypeScript, stop and report:
the other way is to read a family call's arrow in `morphism`/`handsBack` as the coproduct of its alternatives'
(`oneOf`'s `alts`), which is outside `usesOf` and needs #431's owner.

### Where each reader says "no body"

The fact is `Node::declared` (`engine/src/model.rs:405`). Each reader sets it:

- **Python**, `engine/src/python/passes.rs:436-446`: a method decorated `@abstractmethod` (`knowledge::PYTHON_ABSTRACT`,
  `knowledge.rs:520`) or of a class whose bases resolve to `typing.Protocol` (`knowledge::PYTHON_PROTOCOLS`, line 521).
  It goes by the decorator and the class, not by the body: an `@abstractmethod` whose body is code (run through
  `super()`) is still `declared`, and a plain method whose body is `...` or a docstring is not (it runs and gives
  `None`). Both are right for #430: a declared method is never one of a call's alternatives (`plan.js` `oneOf`, line
  984), and the second has a body. The signature's edges are made for every function at line 447.
- **Rust**, `engine/src/rust/passes.rs:199-226`: a trait's `function_signature_item` (no block) is `declared` (line
  220); a `function_item` in a trait is a default body. Signature edges at line 535. A `function_signature_item` in an
  `extern` block (`rust/module.rs:527`) is not a trait's method and stays out of #430.
- **TypeScript**, `engine/src/typescript/passes.rs:121` (`add_declared`): a `method_signature` or
  `abstract_method_signature` is `declared`. These are a class's members (lines 196-205), an `interface`'s and a named
  object type's (`method_signatures`, lines 378-393, called at 249 and 258). Signature edges at lines 980-986. Not
  covered, and left for a later issue: an ambient `declare function f(): T;` (a `function_signature` declared once is
  `Declared::Body` with `declared: false`, line 138), and an interface property of function type
  (`keep: (r: Report) => Receipt`), which reads as a field, not as a method. It is isomorphic to a method signature,
  but the pair does not hold it.

What each reader keeps: the `declared` flag, the signature (`Node::params`, `Node::returns`, the `Takes`/`Returns`
edges), and the method as a member of its class (`Contains`). What it drops: nothing. The arrow is formed empty
downstream.
