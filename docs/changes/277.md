A route serves a set of methods at a path. A Python route whose code lists its methods in another order than Atlas
writes them (`@app.route("/items", methods=["POST", "GET"])`) was labelled `POST|GET /items`, and the same route
written `["GET", "POST"]` was another route: `atlas changes` after swapping the two methods reported a route removed
and one added. Now every way of writing the set, a list in either order, a tuple or a set literal, is the one route
`GET|POST /items` (methods in the order `GET HEAD OPTIONS POST PUT PATCH DELETE`), and swapping them changes nothing.
The picture of every other route is the same.

```text
@app.route("/items", methods=[...])            label before        label after
  ["POST", "GET"]                              POST|GET /items     GET|POST /items
  ["GET", "POST"]                              GET|POST /items     GET|POST /items
  {"POST", "GET"}                              POST|GET /items     GET|POST /items

atlas changes, after ["POST", "GET"] became ["GET", "POST"]
  before   + API · GET|POST /items
           - API · POST|GET /items
  after    nothing changed in the routes, their places or the findings, since HEAD
```

The graph's JSON keeps each route's label and gains, beside it, the requests the route serves
(`"request": {"methods": ["GET", "POST"], "path": "/items"}`), which the page does not read. A request whose method
the code leaves to a value (`requests.request(METHODS[key], url)`) is asked as its path alone (`/api/orders`), where
the JSON wrote `{METHOD} /api/orders`; the requests it meets are the same.
