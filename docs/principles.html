Category theoryhow the parts of a program connect

A category

Functions are arrows, and a route follows them from start to place.

In Atlas

Every step hands its result to the next. You can follow the arrows from where the program starts to where the data ends up.

Without it

Each step reaches into one shared value. Nothing is handed on, so there is no route: you cannot tell what comes first.

Effects in the arrow

What a function does to the world is part of it.

In Atlas

The file a step writes hangs on that step. You see who writes it.

Without it

The file is there, but no arrow leads to it. Something writes it, and the picture cannot say what.

A pushout

The same meaning gives the same picture.

In Atlas

Three languages, three spellings, one thing: an option the caller can change. Atlas draws the thing.

Without it

Drawn by their spelling, a program and its port look like three different programs.

Yoneda

A thing is what it connects to, not what it is called.

In Atlas

A function you renamed but that connects the same is the same function. The diff stays quiet.

Without it

Compared by name, a rename shows as one thing deleted and another added, and the real changes drown in it.

A partial map

What is not built yet is part of the picture.

In Atlas

A design can live in the code before it is built. The dotted part is the work still to do.

Without it

Finished code that already calls the sketch would run on nothing. Atlas asks about it.

Topologywhat stays the same when you zoom in or out

A quotient

Zooming out is gluing, and nothing gets lost.

In Atlas

Closing a box glues its insides into one. The lines in and out stay; open it again and you get the same picture back.

Without it

If zooming out could drop a line, a closed box would hide what it reads, and you could not trust any overview.

Type theorywhat goes into a function and what comes out

Types of arrows

A signature says what goes in and what comes out.

In Atlas

With a return type, the picture follows the value to where it goes next.

Without it

Without one, what the caller gets has no type, and nobody can follow it further.

Liskov substitution

A subclass keeps its base's promise.

In Atlas

Wherever the code expects an exporter, any kind of exporter fits: it takes what the base takes.

Without it

A subclass that asks for more breaks every caller that trusted the base.

Graph theorywhat leads to what

Reach

What a step does, and what it sets in motion, are two things.

In Atlas

Solid: what the step does itself. Dashed: what it causes through the steps it calls.

Without it

Merged, a step seems to do everything it causes, and you look for the write in the wrong place.

A directed graph without cycles

Dependencies go one way.

In Atlas

Packages depend in one direction, so each can be read, tested or replaced on its own.

Without it

Two packages that reach for each other have no order: you cannot take either apart.
