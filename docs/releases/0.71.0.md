Atlas 0.71.0 follows more of what your code says, where it says it: a path looked up in a table the code
writes out, a folder it lists or walks to any depth, a file or a connection it hands on, a file it opens through
options, a path it builds step by step, a value a macro names. Python, Rust and TypeScript read each of these
alike. A name the code binds once is one value wherever it stands, and a name bound to what operators compute of
other names stands for those names, so a loop writes only the files it writes and a step takes the values it is
handed. On the page, a step counts the step that set its object up earlier in the route, and a value a function
makes itself is its own, not a value from beyond. And `atlas-code serve` reads your code once, opens on the
picture the agent reads, and reads again only when a file a reader asked about changes. Four decisions, each
derived from principle on its issue, are drawn beside the points they made.

## A path looked up in a table, a file listed in a folder

A client that looks its paths up in a table it writes out (`PATHS[env]`, `paths.get(key)` of a
`HashMap::from([..])`, an object literal in TypeScript) asked an address the code does not say in TypeScript and
Rust, and met no route. Now a key no code decides is one of the values the table holds, and a key the code
writes picks its own, as Python already read it: the client meets the routes at the paths its table holds, in
all three languages. A folder's listing is `D/*` everywhere (`fs::read_dir`, `readdirSync`, `os.listdir`), and
a `for` loop or a closure run on each element takes one of the elements. In Python, `os.path.join`, `+` and
pathlib's `/` are the same path to every rule that asks.

## A name bound once is one value, and a walk reaches every depth

A loop that uses its element twice in one path (`root / kind / f"{kind}.csv"` for each `kind` of
`["books", "games"]`) drew every pairing of the two uses: `out/books/books.csv` and `out/games/games.csv`, but also
`out/books/games.csv` and `out/games/books.csv`, files no run writes. Now a name the code binds once is one value
wherever it stands, so the route writes the two files it writes. Two lists the code keeps in step only by an index
it counts (`FOLDERS[i]`, `NAMES[i]`) are still two values, and Atlas still draws every pairing of them: the code
does not say they belong together.

A function that lists a folder and calls itself on each folder it finds (`copy_tree(entry, target / entry.name)`)
was followed one call at a time, down to a depth limit: a place for each level of `data/*/*/…`, and at the limit a
folder of a `{source}` no call hands. Now the recursion is followed to where it ends, every folder at any depth
below what the first call hands: the copy reads each file at any depth in `data/` and writes at any depth in
`backup/`, the same place a walk with `rglob("*")` reads. Both hold in Python, Rust and TypeScript.

The same holds for two functions that call each other in turn (`mirror` lists a folder and hands each entry to
`mirror_entry`, which hands a folder back): they are one recursion, followed to where it ends, so `mirror` reads every
file at any depth in `photos/` and writes at any depth in `archive/`.

## A file or a connection keeps the place it was opened at

A Rust server that binds its address in `main` and hands each connection to a function drew the web it talks
to as `Web`, with no address. A connection is a door to the place it was opened at, and keeps that place
wherever it is handed, as a path does: the greeter's `answer` and `linger` reach `Web(127.0.0.1:7878)`, and a
client that connects there reaches the same box, so the two ends of a connection meet. Python's sockets move
data by the same operations as Rust's.

A file is a door too. A function handed an open file (`count(f)`, `emit(out, n)`) read and wrote nothing, so
`atlas-code check` asked of `emit` why it does nothing, and a Node client that connected with
`net.createConnection(7878, "127.0.0.1")` reached no network at all. Now every operation through a door (a `read`,
a `write`, a `sendall`, a listener for `"data"`) is a line of its own to the place the door was opened at, whether
the function opened the door or was handed it, in Python, Rust and TypeScript. An address is `host:port` however
the code writes it: `("127.0.0.1", 7878)`, `SocketAddr::from(([127, 0, 0, 1], 7878))`, or a port and a host handed
apart. The overview still draws one line per place on each side of a step; opening the step shows each operation
in the order it runs.

Each operation goes its way, as a file's does: a receive is read from the address and stands on the left of its
step, a send is written to it and stands on the right, and connecting writes. So a client sends its name from `main`
and hears the greeting in `hear`, with the address between them. Node's descriptors and file handles are doors as
Python's file objects and Rust's `File` are, and an operation goes to the opening that made it, so two files opened
on one line are two places.

## A path is named by what names it, and so is a folder

An input whose default is the empty path names nothing but itself. A program that writes its report to
`process.env.REPORT ?? ""` and its log to `process.env.LOG ?? ""` drew both written into one unnamed place, its two
steps folded into one; now each writes the file its variable names, `Disk({$REPORT})` and `Disk({$LOG})`, and so do
`os.environ.get("REPORT", "")` and `env::var("REPORT").unwrap_or_default()`. A file whose path names no place no
longer takes a literal of its call for a name: `open(os.environ["CARD"])` reads `Disk({$CARD})`, not a file called
`CARD`.

A helper that reads the variable its caller names (`setting(name)` over `os.environ[name]`, `env::var(name)`,
`process.env[name]`) is completed by what each caller hands it, as a path's parameter is. `saveReport` and `saveLog`
hand it `"REPORT"` and `"LOG"`: they were drawn writing into one place named by the call, `Disk(setting(name))`. Now
each writes the file its variable names, and what `saveReport` writes is the box `showReport` reads back.

A folder is placed as the files in it are. Removing `Workbench::of(project).file("report.txt").parent()` removes
`{project}/.made/`, the folder the report is written into, where it was drawn removing `File(report.txt)`, a literal
of the call; Python's `shutil.rmtree` of a `.parent` and TypeScript's `rmSync(dirname(...))` read the same. The
step up `..` names no folder of its own: `{root}/..` rests where `{root}` does. Whether a path starts at a literal
of your code is read from the same table of path functions each reader evaluates paths with; nothing a picture
shows moves by it.

A path taken within its folder and joined back to that folder is the path it came from. `note.relative_to(root)`,
`note.strip_prefix(root)` and Node's `path.relative(root, note)` are one operation in every language, which a join at
the same folder undoes, also where another function joins the key back. So a program that lists its notes and reads
each by its key reads `notes/*`, where it read `notes/notes/*` or a name of its own. A key cut out of the path's text by
its length is still a name Atlas does not follow.

## Forms that say the same thing are read alike

In Rust, a `PathBuf` built with `push`, `set_extension` or `pop` was a value Atlas did not follow, so the recipe a
shelf reads was drawn as `File(shelf)`, the folder it started from. A change in place is now the path bound anew
(`p.push(x)` is `p = p.join(x)`, `p.pop()` is `p = p.parent()`), as a joined path is in Python and TypeScript: the
recipe is `File(shelf/recipes/bread.md)`, and `p.read_dir()` lists the folder and each entry in it, as
`fs::read_dir(p)` does. A value bound through `*` is the value it is written on, a constant named inside `vec![..]`
or `matches!(..)` is a use of the constant, and `tokio::fs` and `async_std::fs` are disk as `std::fs` is.

In TypeScript, a listing with `{ withFileTypes: true }` gives entries whose `name` is the name below the folder, so
`join(DATA, e.name, "meta.json")` is `data/*/meta.json`; `for (const k in KINDS)` goes over the keys the table writes,
each a file of its own; and `process.env[STORE]` with `STORE = "STORE"` is the variable `STORE`. In Python, a
database opened on a file is named by that file however its path is built: `sqlite3.connect(os.path.join("data",
kind, "counts.db"))` was named `data`, and a function that opened `counts.db` and `totals.db` was read as opening
one. Now they are `data/{kind}/counts.db` and `data/totals.db`, in Python as in Rust.

A lookup the library writes as a call (`levels.first()?` and `levels.get(name)?` in Rust, `levels.at(0)` and a
`Map`'s `get` in TypeScript, `next(iter(levels))` and `d.get(k)` in Python) was a step of its own that gave the part
it picked, one box more than the same route written with a subscript. It is now the projection the subscript is: no
step, handed the collection it picks from, and a change of the part it picks changes the collection, as a change of
`rows[0]` does. Which calls are lookups is a table per language. On Atlas's own code, 136 functions lose a lookup step
and hand the collection on.

## A step counts what ran before it

A shelf is handed its folder when it is built, and each of its methods writes its own file there. When `main`
set the shelf up in a step of its own, the page counted only callers above a step, not the step beside it, so
both methods drew the path as it was read, `Disk(write.path)`, and folded into one box. Now a caller that set
the object up counts wherever it ran earlier in the route, and each method writes its own file. Who makes a
path whole is also written in its shortest form: an alternative that contains another says nothing more.

The engine's read-back reads that same order: a call ran before another when it stands before it and no choice
holds the two in different arms, and in a loop every call of the loop ran before every call of it. So a set-up
in a loop counts for every call of the loop, and one in an arm counts for an `if` nested in that arm.

What a step reads back is read in each context it is called in: the route that starts at it, and each chain of calls
that leads to it, with what ran before it there. A set-up the step runs itself counts for what follows it in its
body, never for what came before. In the shortcut of the `order` pair, `review` keeps its report in `out`, then sets
the drafts up and reads the report from there. Nothing in the route writes that file, so the closed `review` reads
it from the left; before, the file was missing until the box was opened.

The page draws that order too. Where an arm ran a step and then a choice of its own (`if KEEP: open_shelf()` and
within it `if REPORT: keep_report()`), the page drew one frame, `one of ● KEEP ● KEEP · REPORT`, as if the two calls
were alternatives, although both run where `REPORT` holds. The inner choice is now a frame inside the arm, after the
step before it, so every frame of a choice holds alternatives only. An arm that runs nothing but one choice is that
choice: an `else` whose only statement is an `if`, or guards with nothing between them, stay one frame, as an `elif` does.

## A name computed of names stands for them

A name bound to what operators compute of names, with no call in it (`let gap = first.db - QUIET.db`,
`let both = [first, &QUIET]`, `const both: Level[] = [first, QUIET]`), was read two ways. Python followed it to the
names it is made of. Rust and TypeScript kept it as a value of the body's own: a step handed `gap` took nothing, a
step handed `both` took `Level · both` in place of the two levels, and the module's quiet level reached neither
step. An operator is no step, and naming its result adds no arrow, so now, in all three languages, a step handed
such a name is handed what the expression written in its place hands: `draw(gap)` takes `first` and `QUIET`, as
`draw(first.db - QUIET.db)` does, and a `vec![..]` of names is the values it holds. The name is still the body's
own. A choice (`a if c else b`, `x ?? y`) and a value a call makes (`samples.abs() > 0`) are read as before.

A list a step then changes in place is no longer those names. `both.push(second)` binds `both` anew, as
`p.push(x)` is `p = p.join(x)` for a path, so from where the body binds it the list is a value of its own: the push
takes that list and `second` and makes it anew, and the step after it takes what the push made. The same holds for a
function of the program's that changes what it is handed (`add(&mut both, second)`), in one arm or in a loop, and in
all three languages. A list written out once (`vec![first, second]`) still stands for the names it holds.

A list the body makes and then changes in one arm of a choice stands in the body's frame, where it is bound, and
what the arm makes of it is the choice's value, which the arm that does not run keeps: the step after the choice
takes that value, not the arm's. A change in a loop takes the body's list, not the loop's element of the same type.

A change of a part is a change of the whole. Where code changes a part it picked by a subscript or a lookup
(`rows[0].push(level)`, `let row = &mut rows[0]`, `rows.at(0)!.push(level)`, `row = rows[0]; row.append(level)`), the
step is handed the collection and gives it anew, and the next step takes the new value. Before, Rust dropped the step,
and TypeScript drew it as a call Atlas could not follow. Where the collection is the module's (`ROWS[0].push(level)`),
the change writes `Global(signal.ROWS)`, in every language.

A Python local's annotation names a type, as Rust's `let both: Vec<Level>` and TypeScript's `const both: Level[]` do:
`both: list[Level] = [first, second]` no longer counts `Level` among the values the function reads.

## A cold reading of Rust code takes a third less time

A cold reading of Atlas's own code took 28.5 s and takes 19.1 s. Most of a reading is linking bodies, not parsing
them, and its cost followed the length of the file a body stands in: tree-sitter finds a node's parent by searching
down from the top of the file, and the Rust reader walked a body once for every kind of node it looked for. One walk

byte for byte, on Atlas and every pair. `--timings` names the stages a reading spends its time in.

## A body's names are climbed once

Atlas asks, for every name in a function's body, where it is read and what binds it. It asked the same name up to three
times, climbing the body's tree each time. Each answer is now kept per node and read from the body's own index, so a

## One reading, one picture for both sides

`atlas-code serve`, and Atlas Studio with it, read a program twice on a cold start: once without its libraries for a
first picture, then again with them. That first picture was no coarser view of the complete one. Its routes ended at
a library's border, where the complete picture follows the library to the place it reaches, so no zoom or filter
leads from one to the other, and the agent beside you read the complete one. Now serve reads once, and the page
opens on the picture the agent reads; after a change it keeps that picture until the next one is drawn. A part's
reading is kept with what its reader asked of the repository, so a file no reader asks about (a picture, a note, a
log) no longer makes Atlas read again or the page redraw. The first picture comes later than 0.70's did (19.8 s against
10.8 s on Atlas itself), and it is the complete one, which 0.70 drew only at 29.8 s.

The agent's text of a route reads the same steps the same way. `route` placed a step's files by the callers on the
path only, so where `main` set a shelf up in a step of its own, the text said `writes write.path` while the page
drew `out/report.txt`. It now reads every step as the page does, what ran before included: a door of a class is read
with the route's entry above it, and a method that may run instead runs in place of the step. Each step the text
tells names the places the page draws there.

`atlas changes` names each construct by the name the page gives it. A method has its class (`Block.scaled`, where
it said `scaled`), an initializer is the call to its class (`Rows()`, where it said `__init__`), a type whose name
another type shares carries its module (`sparse.Rows`), and a sum written in a signature is listed as the page draws
it (`BaseComponent | nn.Module`), where it was listed by an id with the engine's `ext:` tags in it.

The page, `route`, `check` and `changes` now say each function and type through one name. Two types of one name carry
as many of their last modules as tell them apart: `orders.model.Frame` beside `billing.model.Frame`, where both were
drawn `model.Frame` (on Atlas itself, `python.body.Body`, `rust.body.Body` and `typescript.body.Body` were all
`body.Body`). A route's text writes a step as its call (`billing.model.Frame(cents)`), a finding names an initializer
as the call to its class where it said `Frame.__init__`, and a finding counts names over all the program's parts, so
that it is not raised and resolved only because another type came to share a name with the one it names.
