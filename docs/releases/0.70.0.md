Atlas 0.70.0 is the command `atlas-code`. It stops guessing where your code says nothing, works out what a call runs once for every
question that asks, and writes into your tree exactly what it is asked to. A fault in one file or one
call no longer ends the run, and Atlas now measures itself every night. Tensors that jaxtyping
annotates now stand together by rank, a socket and an `app.all` route are the network the code says they are, and a
view of Atlas itself draws in about a second once it is read.

## The command is atlas-code

Other tools install a command `atlas` too (ariga's database toolkit, MongoDB's Atlas CLI), so Atlas
could not be installed beside them. Atlas's command is now `atlas-code`, as its Homebrew package
already was, and the nightly's `atlas-code-nightly`; `alias atlas=atlas-code` keeps the short name.
`brew upgrade`, `atlas update` and the install scripts move an earlier `atlas` over and remove it. The
MCP server keeps its name, `atlas`, so its tools are named as before; an agent registered with
`atlas mcp` is registered again with `atlas-code mcp`. And an update is now announced only once all of
its files are there: Studio offered 0.69.3 while its installers were still being built.

## Where the code says nothing, Atlas no longer guesses

A method called `home()` was your home directory to Atlas, whatever object it was called on, and so
were `joinpath`, `with_suffix`, `parent` and `Path(..)`: Atlas went by the name. Now a library's fact
holds only where ty finds that library. Your own `Archive.home()` is followed into its own code, and
where ty cannot say what a value is, the place keeps the name the code gives it instead of a guess.
A class of your own named `Path` is yours too, and Atlas reads a project's `pyproject.toml` and `ty.toml` through the
same one reading as the rest of its files.

Example: home

## A path's directory is the path without its last part

A log written beside the data file `~/data/{name}` lies in `~/data`, also where a caller hands the path: 0.69.3 drew
it as a file of its own, `~/data/{name}/../shelf.log`. So in Python (`.parent`), Rust (`Path::parent`) and
TypeScript (`path.dirname`).

## Tensors of one rank stand together

A program that annotates its tensors with jaxtyping (`Float[Tensor, "batch dim"]`) drew every shape as a place of
its own, so a model's components read as many short, separate flows. Now each shape stands in its rank family, the way
a subclass stands in its base class: `Float Tensor · 2D` stands for the rank-2 float tensors in the picture, and a
click opens it into the exact shapes. Names still count (`batch dim` and `batch ndim` are two types of one family),
and so does the dtype: an `Int` tensor never joins a `Float` family.

Compare: changes/298-concat-before.png = 0.69: `Concatenate2D` takes a `batch _` and gives a `batch ndim`; changes/298-concat-after.png = 0.70: both are rank 2, `Float Tensor · 2D`; changes/298-concat-open.png = 0.70, the family opened: each value in its frame

## What a call runs is one answer

Which functions may this call run? The route, what a parameter holds and which errors a call hands
on now all ask that one question, and get one answer. A value built at the call runs its own class's
method; a value of a declared class may run every override below it; a call through a class runs that
method and no override. The step says so too: a call that may run two functions reads `Section.show · one of 2`,
named by the class it runs on. Rust is read by the same law: a unit struct's method (`Plain.show()`), a supertrait's
method called on a `&dyn Block`, and a function named like its crate are followed into the code they run.

## The network, as the code says it

A Rust server that reads from and writes to a `TcpStream` drew no place at all, and `atlas-code check` asked whether
it did anything. What moves data on one of std's sockets (connecting, reading, writing, sending, receiving) now reaches
the web, as it does through Python's `socket`; binding an address, accepting a connection and shutting a half move
none. And an Express `app.all(path, ..)` route serves every method: a `POST` to its path met no route and left for the
web, and now meets the handler in its own program.

Compare: changes/291-before.png = 0.69.3: a server that greets its clients touches nothing; changes/291-after.png = 0.70.0: `answer` and `linger` reach the web; changes/280-before.png = 0.69.3: the page's POST meets no route and leaves for the web; changes/280-after.png = 0.70.0: the `app.all` route serves every method, the POST among them

## The wheel zooms wherever the pointer is

The mouse wheel sometimes did nothing until `+` was clicked. Five strips over the picture took the wheel without
using it: the empty part of the state bar, the zoom's buttons, the legend, the hint and the status bar. A drag let go
outside the page (over Studio's bar) kept panning with every move after it; a wheel made while `atlas-code serve`
hands the page a new reading was lost; and opening a box far larger than the window sank the scale below the zoom's
floor, from where a wheel out jumped in. Now the wheel zooms wherever the pointer is and whatever the page is doing.

## The page and the agent keep their notes whole

The page and your agent write the same notes. When both wrote at once, a note could vanish; now a
lock between the two makes one wait for the other. `atlas serve` answers every request within
bounds, and what changes something answers only its own page, never another website.

## A fault stays where it happens

One panic inside ty, one MCP tool call that fails, one notebook that does not parse: in 0.69.3 any
of them ended the whole run. Now that one file is read untyped, that one call answers an error, and
everything else goes on.

## Letters past z, and an exit status CI can read

Steps past `z` go on as `aa`, `ab`, as a spreadsheet names its columns, so no label names two
branches. `atlas-code check` exits 1 when it has questions and 2 when it could not read.

## Atlas measures itself, every night

Every night Atlas builds itself, reads itself and a handful of public programs, cold and warm, and runs
its tests, and keeps the numbers. A night that is slower than the ones before is only a reason to look:
the same run measures that commit against the last good one, turn and turn about on the same machine. Only
what that reproduces is reported, and its size says how urgent it is. Every Monday `next` is held against
the last release, so that creep shows too, and any stretch of history can be searched for the landing
that made it slower. It all runs at night, so no commit pays for it.

## A view of Atlas in about a second

Drawing a view worked out what every function reads back and changes again and again, each time copying what it
already knew; reading a program walked each function body again for every name it followed. Now each answer is kept
once and shared, and a body is read once for every question its steps ask. The picture is the same, byte for byte;
on Atlas itself a warm view takes about a fifth of the time and a third of the memory (561 MB at its peak before,
211 MB after), and a cold one about a third of the time.

Bars: Cold view of Atlas, before = 55 s; Cold view of Atlas, 0.70.0 = 20 s; Warm view of Atlas, before = 5.9 s; Warm view of Atlas, 0.70.0 = 1.0 s | `atlas-code view` of Atlas itself, release builds, before and after #287 and #289, the median of three to five runs on a shared machine; measured again on a quiet one with the release.
